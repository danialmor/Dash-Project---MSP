# برنامه‌ی پلتفرم Danimor — یک دامین، یک هاست، چند سایت

نسخه‌ی برنامه: ۱٫۰ · وضعیت: مرحله‌ی ۱ (زیرساخت) انجام و آزمایش شده است.

## ۱. هدف‌ها (از گفته‌های شما)
1. چند سایت با کاربری متفاوت زیر **یک دامین و یک هاست**: `danimor.com/msp-bi`، `danimor.com/aide` و بعدی‌ها.
2. صفحه‌ی اول فقط **لوگوی متحرک**، بدون لینک و دکمه؛ کسی که سیستم را می‌شناسد آدرس را مستقیم می‌زند.
3. **همه‌چیز آنلاین ذخیره شود**؛ روی دستگاه چیزی ماندگار نماند. بدون اینترنت فقط یک «صف موقت» باشد و با اتصال منتقل شود.
4. **مرکز کنترل و مدیریت**: کاربران و کدها، دسترسی هر کاربر به هر سایت، سایت‌ها، سلامت همگام‌سازی، رویدادها، پشتیبان.
5. **اتصال Aide (تقویم منشی)**: بتواند جلسه ثبت کند و کاربران و کدشان را ببیند.
6. تغییرات اینجا انجام شود ← در گیت‌هاب بارگذاری شود ← هاست خودکار از گیت‌هاب بگیرد.
7. **هوش مصنوعی محلی**، فقط مال هاست خودتان، بدون وابستگی بیرونی.

## ۲. دو نکته‌ی صادقانه درباره‌ی «بدون سرور»
- **ذخیره‌ی آنلاین یعنی حتماً یک جایی کد در حال اجرا و یک پایگاه‌داده**. مرورگر نمی‌تواند داده‌ی مشترک چند نفر را نگه دارد. پس حداقلِ لازم یک سرور کوچک است (نه یک سرویس بیرونی). راه‌حل: **یک VPS کوچک** که هم سایت‌ها و هم «هاب» روی آن است. نتیجه: چیزی بیرون از اختیار شما نمی‌ماند.
- **هوش مصنوعی واقعی (مدل زبانی) روی هاست اشتراکی (cPanel) اجرا نمی‌شود**؛ حافظه و پردازش زیاد می‌خواهد. گزینه‌ها در بخش ۹ آمده است.
(امروز Aide روی Cloudflare Worker+D1 است؛ یعنی «بیرونی» محسوب می‌شود. بخش ۸ مسیر انتقال را می‌دهد.)

## ۳. معماری
```
                   https://danimor.com
 مرورگر / iPad ──────────────┐
                              ▼
                  ┌──────────── Caddy (HTTPS خودکار) ───────────┐
                  │  /            → لوگوی متحرک (static)         │
                  │  /msp-bi/     → سایت کنترل پروژه (static)     │
                  │  /aide/       → سایت Aide (static)           │
                  │  /admin/      → مرکز کنترل (static)          │
                  │  /shared/     → SDK مشترک                    │
                  │  /api/*   ──► Hub (پایتون، 127.0.0.1:8787)   │
                  └──────────────────────┬───────────────────────┘
                                         ▼
                   SQLite (WAL) در /var/lib/danimor  +  پشتیبان روزانه
                                         ▼ (اختیاری، بعداً)
                              Ollama (مدل زبانی محلی) ← /api/v1/ai
```
- سایت‌ها فقط فایل ثابت‌اند. همه‌ی داده و ورود از طریق Hub است.
- هر سایت یک «شناسه» (slug) دارد (`msp-bi`، `aide`، …) و داده‌اش در همان فضا می‌ماند؛ کاربر فقط به سایت‌هایی که دسترسی گرفته وارد می‌شود.

## ۴. تصمیم‌ها و دلیلشان
| موضوع | تصمیم | دلیل / جایگزین |
|---|---|---|
| ساختار آدرس | مسیر (`/aide`) نه زیردامنه | مطابق خواسته. هزینه‌اش: همه‌ی سایت‌ها هم‌مبدأ هستند؛ XSS در یکی روی بقیه اثر می‌گذارد ← اسکریپت بیرونی ممنوع، CSP در مرحله‌ی ۵. اگر ریسک بالا رفت، به زیردامنه می‌رویم. |
| بک‌اند | Hub کوچک با پایتون (فقط کتابخانه‌ی استاندارد) | بدون وابستگی، قابل ممیزی، **کاملاً آزمایش‌شده در همین مرحله**. جایگزین: PocketBase (خوب ولی اینجا قابل آزمایش نبود)، Supabase self-host (سنگین)، PHP+MySQL (برای هاست اشتراکی؛ بدون پیجر زنده و AI). |
| پایگاه‌داده | SQLite حالت WAL | برای ۴۰ کاربر کاملاً کافی، پشتیبان‌گیری ساده (یک فایل). |
| مدل داده | رکورد عمومی: (سایت، مجموعه، شناسه، JSON، شماره‌نسخه) | افزودن سایت جدید بدون تغییر سرور. هزینه: پرس‌وجوی رابطه‌ای محدود؛ ماژول‌های سنگین (نامه‌ها، گزارش‌ها) بعداً جدول اختصاصی می‌گیرند. |
| ورود | کد کاربری + PIN (scrypt)، توکن امضاشده، قفل پس از ۵ اشتباه، ابطال فوری با تغییر رمز/غیرفعال‌سازی | مطابق «کاربران با کدشان». بعداً: TOTP برای مدیر، Passkey. |
| آفلاین | **فقط صف ارسال** (IndexedDB). پس از تأیید سرور از صف پاک می‌شود. | مطابق «لوکال ذخیره نشود». خواندن بدون اینترنت فقط آخرین نمای همان صفحه است (در حافظه، نه ماندگار). |
| تعارض | هر رکورد شماره‌نسخه دارد؛ نوشتن با نسخه‌ی قدیمی رد می‌شود (۴۰۹) و **هرگز بی‌صدا دور ریخته نمی‌شود**؛ کاربر انتخاب می‌کند «تغییر من» یا «نسخه‌ی سرور» | همان اصلی که در Aide خودتان (CAS/۴۰۹) پیاده شده است. |
| خروج از حساب | تا وقتی تغییر ارسال‌نشده هست، خروج نمی‌دهد | جلوگیری از گم‌شدن کار (مثل «قفل میز» در Aide). |
| بروزرسانی زنده | SSE (`/api/v1/stream`) + نظرسنجی | برای پیجر منشی و تقویم. |
| پشتیبان | روزانه ۰۳:۳۰ (۳۰ نسخه) + دانلود JSON از مرکز کنترل + نسخه‌ی بیرون‌سرور هفتگی (مرحله‌ی ۵) | همه‌ی داده فقط روی سرور است؛ پشتیبان حیاتی‌ترین بخش است. |

## ۵. مرکز کنترل (`/admin/`)
**انجام شده (v1):** نمای کلی (سلامت، تعداد کاربر/سایت/رکورد، تغییرات و ورودهای ۲۴ ساعت، ورودهای ناموفق، صف و تعارض دستگاه‌ها) · ثبت و فعال/غیرفعال‌کردن سایت‌ها · کاربران با کد، نقش و دسترسی هر سایت، رمز جدید، غیرفعال‌سازی (قطع فوری نشست‌ها) · همگام‌سازی (هر دستگاه، آخرین ارتباط، تعداد در صف و تعارض) · رویدادها (ممیزی با فیلتر) · کلید اتصال سایت‌ها (مثل Aide) · آزمون هوش مصنوعی · پشتیبان‌گیری و خروجی کامل.
**بعدی (مرحله‌ی ۲ تا ۵):** نسخه‌ی هر سایت و یادداشت انتشار · پرچم قابلیت‌ها برای هر نقش · ارسال اطلاعیه به همه‌ی سایت‌ها · مرورگر داده · ویزارد بازیابی پشتیبان · هشدار (ایمیل/پیام) برای قطعی و پشتیبان‌نگرفتن · مدیریت فایل‌ها · TOTP مدیر.

## ۶. روند گیت‌هاب ← هاست
```
اینجا تغییر می‌دهیم ← بسته/فایل ← مخزن گیت‌هاب (main)
      ← Actions: آزمون‌ها (هاب + SDK) ← اگر سبز بود ← rsync با SSH به سرور
      ← Hub ری‌استارت ← بررسی /api/v1/health ← (قرمز شد؟ استقرار «ناموفق» و نسخه‌ی قبل سر جایش)
```
- **آیپد**: چون پوشه‌آپلود در گیت‌هاب سخت است، بسته‌ی `danimor-platform.zip` را آپلود می‌کنید و Action «unpack-bundle» را اجرا می‌کنید؛ همه‌ی فایل‌ها با ساختار درست باز و commit می‌شوند. بعد از آن هر تغییر خودکار تست و منتشر می‌شود.
- **تناوب پیشنهادی**: هر چند تغییر که تأیید کردید یک «انتشار» (یک بسته). هر انتشار شماره‌ی نسخه دارد و برگشت = revert همان commit.
- **داده‌ها و تنظیمات سرور هرگز با استقرار پاک نمی‌شوند** (`/var/lib/danimor`، `/etc/danimor`).
- **رازها**: کلید SSH استقرار فقط در Secrets گیت‌هاب است؛ کاربر `deploy` روی سرور فقط اجازه‌ی ری‌استارت همین سرویس را دارد.

## ۸. اتصال Aide
جزئیات فنی: `docs/AIDE-CONTRACT-fa.md`. خلاصه:
- امروز Aide: سایت روی GitHub Pages، API روی Cloudflare Worker، دیتابیس D1 (حساب‌ها، نشست‌ها، فضای کار JSON با نسخه‌ی SHA-256 و ۴۰۹). اصول ایمنی همان است که در Hub پیاده شد.
- **الف۱ (پیشنهاد اول، کم‌ریسک):** Aide همان‌طور که هست می‌ماند و فقط «جلسه‌ها» را به Hub هم می‌فرستد/می‌خواند؛ کاربران و کدها از Hub خوانده می‌شود. هیچ داده‌ی فعلی Aide جابه‌جا نمی‌شود.
- **الف۲ (هدف نهایی):** وقتی Hub ثابت شد، حساب‌ها و فضای کار Aide هم به Hub می‌آید و Cloudflare کنار می‌رود (مطابق «بدون وابستگی بیرونی»). این کار فقط با پشتیبان کامل D1 و دو بار آزمون انجام می‌شود.
- صفحه‌ی `/aide/` اکنون «نقطه‌ی اتصال و آزمون» است (ورود با کد، فهرست کاربران، ثبت جلسه، هشدار هم‌پوشانی، صف آفلاین)؛ بعداً Aide اصلی جایگزین آن می‌شود.

## ۱۰. امنیت و ریسک‌ها
- **یافته‌ی مهم:** داده‌ی واقعی پروژه‌ها (JSON/xlsx) اگر کنار سایت قرار بگیرد **عمومی** است. به همین دلیل در این مرحله داده‌ی واقعی در بسته نیست و در مرحله‌ی ۲ پشت ورود می‌رود. `robots.txt` و `noindex` امنیت نیستند.
- سرویس‌ورکر: پاسخ‌های `/api/` و `/data/` هرگز ذخیره نمی‌شوند (اصلاح شد).
- توکن در `localStorage` است (ساده و سازگار با آیپد). نشت آن فقط با XSS ممکن است؛ پس اسکریپت بیرونی نداریم و CSP می‌آید. ابطال: تغییر رمز یا غیرفعال‌سازی کاربر فوراً توکن‌ها را می‌کشد.
- ورود: scrypt، قفل ۱۰ دقیقه‌ای پس از ۵ اشتباه، همه‌ی رویدادها در ممیزی.
- نقطه‌ی شکست واحد: یک سرور. کاهش: پشتیبان روزانه + بیرون‌سرور + دستورالعمل بازسازی؛ در صورت نیاز بعداً سرور دوم.
- **محدودیت‌ها:** هیچ سامانه‌ی مرورگری صفر از دست رفتن داده را تضمین نمی‌کند (خاموشی دستگاه هنگام صف). به همین دلیل وضعیت ذخیره همیشه نمایش داده می‌شود و خروج با صف باز مسدود است.

## ۱۱. چه چیزی از شما لازم دارم
1. دامین `danimor.com`: ثبت‌شده است؟ دسترسی به DNS دارید؟
2. کاربران عمدتاً کجا هستند (ایران/خارج)؟ روی انتخاب کشور سرور و روش پرداخت اثر دارد.
3. الف۱ یا الف۲ برای Aide؟ (پیشنهاد: الف۱ بعد الف۲)
4. اجازه برای خواندن `cloudflare/worker.js` در مخزن aide تا مدل رویداد دقیق تطبیق داده شود (مرحله‌ی ۳).
5. فهرست نقش‌ها و افراد اولیه (کد و نام) برای ساخت کاربران.
